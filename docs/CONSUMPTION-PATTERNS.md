# Consumption Patterns

How to use this template in a consuming project. Three patterns are supported in v1; pick by use case.

Note on naming: "pattern A/B/C" here refers to how you consume this template (where the harness lives). The "Pattern A vs B" in `PATTERN-A-VS-B.md` is a separate concept about multi-agent coordination within journeys. The two naming schemes do not interact.

## Decision tree

If you can answer "yes" to any of these, the pattern in the same row is your default.

| Question | Pattern |
|---|---|
| Is the tested app a project where you want QA findings in their own commit history, separate from app code? | A. Sibling repo via `gh repo create --template` |
| Are you experimenting or running an internal-only one-off? | B. Local clone, no GitHub remote |
| Do you want to pull upstream harness improvements via `git pull upstream master`? | C. Fork via GitHub UI |

If multiple rows apply, the one earlier in the table usually wins.

## Pattern A: Sibling Repo (default, most documented)

A new GitHub repository created from this template. The QA repo lives next to the tested app's repo, not inside it.

**Setup:**

```bash
# Create the new repo from the template
# gh repo create --clone places the repo in the current directory; cd to the parent first
cd ~/projects
gh repo create my-app-qa \
  --template yhyatt/agent-qa-harness-template \
  --private \
  --clone

cd my-app-qa

# Run the interactive scaffolder
./scripts/scaffold.sh

# Install dependencies
npm install

# Capture auth fixtures (one-time, headed browser)
npm run populate-auth

# Smoke-test against staging
TEST_TARGET_URL=https://my-app.vercel.app npm run test:e2e -- --grep "J4"
```

**CI implications:** the QA repo gets its own `.github/workflows/ci.yml`. The no-auth journey (J4) runs on every PR. The tested app's repo is not touched. The only coupling between the two repos is the environment variable `TEST_TARGET_URL`, which the QA repo's CI sets at runtime.

**When to skip A:** the tested app lives in an org with a strict repo budget; you want harness findings to appear inline on the app's PRs rather than on a separate QA repo; you want one checkout for everything.

## Pattern B: Local Clone, No Remote

Clone the template locally, sever the git history, scaffold, and never push to GitHub. Useful for a quick exploration where the output is disposable.

**Setup:**

```bash
git clone https://github.com/yhyatt/agent-qa-harness-template ~/projects/my-app-qa-scratch
cd ~/projects/my-app-qa-scratch

# Sever from the template's upstream history
rm -rf .git
git init
git add .
git commit -m "init from agent-qa-harness-template"

# Run the interactive scaffolder
./scripts/scaffold.sh

npm install
npm run populate-auth
TEST_TARGET_URL=https://my-app.vercel.app npm run test:e2e -- --grep "J4"
```

**Caveats:** no CI, no shared visibility, no history. The `.qa-runs/` directory is gitignored; findings accumulate locally and vanish when you delete the directory. Anyone else on the team cannot see the run results.

**When to skip B:** anything past a one-off exploration. Once you decide to keep the harness, migrate to A or C.

## Pattern C: Fork via GitHub UI

Fork `yhyatt/agent-qa-harness-template` on GitHub, then add the upstream remote so you can pull harness improvements as the template evolves.

**Setup:**

```bash
# 1. Fork via GitHub UI: https://github.com/yhyatt/agent-qa-harness-template -> Fork

# 2. Clone your fork (replace <your-fork-name> with the exact name you gave the fork at fork time)
gh repo clone <your-fork-name> ~/projects/my-app-qa
cd ~/projects/my-app-qa

# 3. Add the upstream remote so you can pull improvements later
git remote add upstream https://github.com/yhyatt/agent-qa-harness-template.git

# 4. Run the scaffolder
./scripts/scaffold.sh

npm install
npm run populate-auth
TEST_TARGET_URL=https://my-app.vercel.app npm run test:e2e -- --grep "J4"
```

**Pulling upstream improvements:**

```bash
git fetch upstream
git merge upstream/master
# resolve any merge conflicts between your customized adapter files and upstream changes
```

The files most likely to conflict are `playwright.config.ts`, `scripts/scaffold.sh`, and `tests/e2e/journeys/journeys.spec.ts`. Adapter files under `tests/e2e/adapters/` are generated by the scaffolder and are yours; they do not exist in the upstream template, so they will not conflict.

**When to skip C:** if you will never want upstream changes, just use A. A gives you a clean repo without the overhead of managing an upstream remote.

## Pattern D: In-Repo Subdirectory (not yet supported in v1)

Copying the harness into a subdirectory of the tested app (single-repo workflow) is on the BACKLOG but not validated end-to-end. The current scaffolder assumes a fresh repo and edits `README.md` and `.github/workflows/ci.yml` unconditionally; running it in a subdirectory of an existing app will either fail or clobber files.

If you want this pattern, file an issue describing your stack and we will work out the right boundary (separate `qa/package.json`, scaffolder flags, etc).

For now: pick A, B, or C.

## Future Patterns (Not Yet Supported, on the Backlog)

- **npm package:** `npm install -D @yhyatt/agent-qa-harness && npx qa-harness init`. Requires repackaging the template as a package with a separate `bin/` entrypoint, no `tests/` shipped, and a locked schema in `dist/`.
- **gh extension:** `gh qa init`. Wraps the same scaffolder behind a CLI verb. Cleaner UX than `gh repo create --template`.

If you would benefit from either, file an issue on the template repo.

## Migration Between Patterns

Moving from B (local clone) to A (sibling repo) is a fresh `gh repo create --template` and re-authoring of journeys; the harness scripts do not carry state between checkouts. Moving from A to C is a fork of the existing sibling repo and adding an upstream remote. There is no migration tooling because each move is small enough to do by hand.
